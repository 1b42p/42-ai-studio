# 42 AI Studio

Сайт для создания видео с помощью ИИ. Пользователь ставит задачу, агент-видеограф
собирает Remotion-композицию, озвучивает, рендерит и отдаёт готовый ролик.

## Запуск с нуля

```bash
cp .env.example .env        # значения-заглушки, секретов в образце нет
docker compose up -d        # Postgres и хранилище, бакеты studio-dev и studio-test
npm install
npm run db:migrate          # применяет миграции к базе из DATABASE_URL
npm run dev
```

Проверить, что всё поднялось:

```bash
curl -i http://localhost:3000/api/health     # {"status":"ok","checks":{"database":"ok","storage":"ok"}}
curl -i http://localhost:3000/eve/v1/health  # {"ok":true,...}
```

`GET /api/health` отвечает `503`, если недоступна база или хранилище; тексты
ошибок при этом уходят только в журнал сервера.

### Как вручную увидеть отказ хранилища

```bash
S3_ENDPOINT=http://localhost:1 npm run dev
curl -i http://localhost:3000/api/health
# {"status":"error","checks":{"database":"ok","storage":"error"}}
```

## Состояние eve

Каталог `.eve/.workflow-data` хранит состояние запусков eve (сессии, потоки,
очереди). Это требование eve: в рабочей среде каталог должен лежать на
постоянном диске и переживать перезапуск процесса, иначе durable-сессии и
идущие ходы теряются. В разработке он создаётся сам.

Не запускайте `npm run dev` и `npm run test:http` одновременно: `withEve()`
держит один dev-сервер eve на корень проекта, и экземпляр тестов делит его с
разработкой — проверки входа в тестах начинают отвечать 401. Остановите один
из процессов перед запуском другого.

## Модель агента

Модель задаётся переменными `AGENT_MODEL` и `AGENT_REASONING`; без
`AGENT_MODEL` (и без `APP_TEST_MODE=1`) сервер не стартует. Для
OpenAI-совместимого провайдера задайте `AGENT_MODEL_BASE_URL`,
`AGENT_MODEL_API_KEY` и `AGENT_MODEL_CONTEXT_TOKENS`; для AI Gateway достаточно
`AGENT_MODEL` и ключа `AI_GATEWAY_API_KEY`, который читает сам AI SDK.

## Песочница Daytona

Задайте `SECRETS_ENCRYPTION_KEY` в `.env`: результат `openssl rand -base64 32`.
Храните его отдельно от базы и сохраняйте при переносе приложения: смена ключа
без перешифрования делает сохранённые секреты нечитаемыми. Сервер проверяет
строгий base64 и длину 32 байта при запуске; сборке секреты не нужны.

После миграций добавьте API-ключ Daytona через стандартный ввод из защищённого
файла (не вставляйте секрет в аргументы команды):

```bash
npm run daytona:add-key -- основной < /путь/к/файлу-с-ключом
```

В базе остаётся только AES-256-GCM-шифротекст. Команда печатает идентификатор
записи и права ключа. Ключи образуют пул: новая песочница создаётся на ключе
со свободной квотой, а отключение ключа не мешает восстановлению уже созданной
песочницы. Если второй ключ той же организации уже есть, команда предупреждает,
что они делят одну квоту.

`DAYTONA_API_URL` задаёт API, `SANDBOX_CPU`, `SANDBOX_MEMORY_GB` и
`SANDBOX_DISK_GB` — ресурсы (по умолчанию 2 vCPU, 4 GiB, 8 GiB).
Песочница создаётся из `agent/sandbox/Dockerfile`, автоматически останавливается
через 15 минут бездействия и архивируется после семи суток остановки.
Автоудаление выключено. Следующее обращение восстанавливает ту же файловую систему.
Песочницы приложения помечены меткой `studio_session` с идентификатором сессии;
остановленная или архивная машина продолжает занимать лимиты аккаунта, поэтому
после ручных прогонов их удаляют командой
`npm run daytona:cleanup -- <appSessionId>` (или `-- --all`). Удаление строки
`sandboxes` или пользователя машину в Daytona не удаляет.

### Ключи Daytona

Квота принадлежит организации Daytona, а не ключу: несколько ключей одной
организации делят одно место. В `daytona_keys` лежат шифротексты, `usage` —
последнее прочитанное использование, `usage_checked_at` — время последней
попытки, `exhausted_until` — до какого времени пул считается исчерпанным.

Форма `usage`, которую читает админка:

```json
{
  "source": "daytona",
  "fetchedAt": "2026-11-04T19:38:35.751Z",
  "organizationId": "organization-id",
  "region": "eu",
  "cpu": { "used": 6, "quota": 10 },
  "memoryGb": { "used": 9, "quota": 10 },
  "diskGb": { "used": 30, "quota": 30 },
  "maxPerSandbox": null,
  "error": null
}
```

`source` — `daytona` или `error`; `fetchedAt` — последнее успешное чтение;
`cpu`, `memoryGb`, `diskGb` — `{used, quota}` в vCPU и ГиБ; `maxPerSandbox` —
пределы на одну песочницу или `null`; `error` — `unauthorized`, `forbidden`,
`unavailable`, `unexpected` или `null`. При ошибке прежние числа сохраняются,
`error` заполняется, а `usage_checked_at` сдвигается. Ответ Daytona, тексты
исключений и значение ключа в базу и журнал не попадают.

Правила выбора:

- Включённые неудалённые ключи перебираются по `created_at`, затем `id`.
- Использование моложе 30 секунд не перечитывается. `usage` помнит
  `organizationId`; если `GET /api-keys/current` его не вернул, берётся
  единственная организация из `GET /organizations`, иначе `organizationId`
  любой песочницы этого ключа. Когда организацию определить нельзя, в `usage`
  пишется `unexpected`, и ключ не блокируется.
- Из `regionUsage` берутся записи `container` (не `linux-vm` и не `windows`)
  и не из служебного региона `earth`; при нескольких подходящих — регион по
  умолчанию организации (`defaultRegionId`). Единицы — vCPU, ГиБ памяти,
  ГиБ диска.
- Ключ подходит, если `quota - used - reserved >= need` по всем измерениям.
  `reserved` — строки `sandboxes` в `starting` моложе 5 минут: создание
  резервирует vCPU, память и диск, пробуждение остановленной — только vCPU и
  память (диск уже занят ею), восстановление из архива — всё.
- Ключи одной организации — один пул, представитель — ключ с наименьшим
  `created_at`. Исчерпанный пул пропускается целиком.
- `unauthorized` исключает ключ из выбора. `forbidden`, `unavailable` и
  `unexpected` без прежних чисел выбор не останавливают.
- Если Daytona отказала при создании по квоте (`400` и сообщение
  «Total … limit exceeded»), пул помечается исчерпанным на 60 секунд, и выбор
  переходит к следующему ключу; `401` исключает ключ. Любой другой `400` даёт
  `sandbox_create_failed`.
- Нет ни одного включённого неудалённого ключа — `no_daytona_key`; ключи есть,
  но места нет — `capacity_exhausted`.

Остановленная контейнерная песочница занимает диск до архивации, поэтому на
Tier 1 при диске 8 ГиБ неархивных песочниц не больше трёх. Отключение
(`enabled = false`) не мешает просыпаться уже созданным песочницам, но новые
на ключе не создаются. Удаление (`deleteKey`) ставит `deleted_at`, отключает
ключ и удаляет его песочницы; шифротекст заменяется маркером `deleted` только
когда удалить удалось все машины. Если часть не удалилась, шифротекст
сохраняется, и операцию можно повторить. Переписка, события и файлы остаются
в базе и S3; следующее сообщение сессии создаёт новую пустую песочницу на
другом ключе.

Ключ Daytona принадлежит одной организации. `GET /api-keys/current` отдаёт
`organizationId` необязательным полем; `GET /organizations` перечисляет
организации владельца ключа, а не самого ключа, поэтому при нескольких
организациях нужен `organizationId` песочницы. Запрос
`GET /organizations/{id}/usage` принимает ключ с правом `read:billing` или
`write:sandboxes`; для создания и удаления песочниц достаточно
`write:sandboxes` и `delete:sandboxes` (чтение песочниц выдаётся всегда).
Документация Daytona расходится по памяти Tier 1 (10 и 20 ГиБ в разных
таблицах), поэтому числа не зашиты, а читаются из ответа использования.

Команды работают от root. Образ `agent/sandbox/Dockerfile` содержит Python 3.12,
Node 24, библиотеки Chrome, шрифты с кириллицей и эмодзи и шаблон Remotion
4.0.538 в `/opt/remotion`. Chrome Headless Shell ставится при сборке командой
`npx remotion browser ensure` и лежит в `/opt/remotion/node_modules/.remotion`.
В образ входят `sandbox-vcpu` (число vCPU по квоте cgroup) и `sandbox-selfcheck`
(версии Node, Python и Remotion, запуск браузера, русский шрифт, один кадр
композиции `Main`). Новый проект собирается копированием шаблона и ссылкой
`node_modules` на `/opt/remotion/node_modules`.

Документацию и страницы агент читает инструментом `read_page` на сервере
приложения: песочница до обычных сайтов не ходит. Поиск — `web_search` через
Tavily (`TAVILY_API_KEY`, необязательный `TAVILY_API_URL`). Без ключа сервер
стартует, а поиск сообщает, что он не настроен; имена страниц Remotion тогда
берутся из `https://www.remotion.dev/llms.txt`. Адреса внутренней сети,
служебные IP и ссылки с логином `read_page` не открывает.

Навыки Remotion ставятся из того же тега, что и `ARG REMOTION_VERSION`:

```bash
npx skills add https://github.com/remotion-dev/remotion/tree/v4.0.538/packages/skills --skill remotion-create remotion-docs remotion-markup remotion-multimedia remotion-render remotion-captions remotion-interactivity --subagent root -y
```

Образ проверяется созданием песочницы и командой `sandbox-selfcheck`:

```bash
daytona create --dockerfile agent/sandbox/Dockerfile --cpu 2 --memory 4 --name studio-image-check
```

`--memory` задаётся в гигабайтах. Повторное создание берёт кэш декларативного
образа: Daytona держит его на раннере 24 часа.

При сборке `prepare` собирает workspace и навыки в JSON-артефакт через
`ctx.populate`, без Daytona и базы. При создании песочницы файлы доставляются
одним пакетом: `workspace/` → `/workspace`, навыки с вложенными файлами →
`$HOME/.agents/skills`. `$HOME` определяется внутри живой песочницы.
Изменение начальных файлов влияет только на новые песочницы.

На тарифах Tier 1/2 доступны только сервисы белого списка Daytona, в том числе
npm, PyPI, GitHub и Hugging Face. Произвольные сайты и YouTube из песочницы
недоступны; настройка отдельной песочницы это ограничение не снимает.
Фоновый процесс сам по себе не сбрасывает таймер автостопа.

Песочница работает от `root`; память и CPU соответствуют `SANDBOX_MEMORY_GB` и
`SANDBOX_CPU`. Многострочные скрипты сохраняют кавычки, heredoc и `$(…)`.
Фоновый процесс переживает конец хода. После внешней остановки следующее
сообщение восстанавливает ту же песочницу с файлами в `/workspace` и `/tmp`.
В Daytona на сессию приходится одна песочница. Неверный ключ даёт
`sandbox_create_failed` с русским сообщением без значения ключа.

## Фоновые команды

`bash` ждёт команду 30 секунд. Не успевшая команда продолжает работу в
песочнице отдельной группой процессов и возвращает `status: "running"` с
каталогом `/tmp/.eve/jobs/<8 шестнадцатеричных знаков>/`: там лежат `stdout`,
`stderr`, `pid` и появляющийся по завершении `exit`. Карточка команды
показывает итог, даже если вкладка была закрыта: сервер хранит задание в
таблице `bash_jobs` (`app_session_id`, `job_id`, `status`, `exit_code`,
хвосты и размеры потоков, время) с уникальностью по паре «сессия, задание».

Строку создаёт идемпотентный синхронизатор событий сессии, а не отдельный
хук: результат `bash` приходит в поток событием `action.result`, и запись
оказывается в той же транзакции, что и событие. Сбой синхронизации не
оставляет задание без строки — следующий проход её досоздаёт; повторная
вставка ничего не меняет.

Карточка опрашивает `GET /api/sessions/<id>/jobs/<jobId>`. Маршрут требует
вход и сессию этого пользователя, `jobId` — ровно восемь шестнадцатеричных
знаков; всё остальное — `400`, чужая сессия и неизвестное задание — `404`.
Сегменты `..` и `%2e%2e` нормализуются URL ещё до маршрута (как пустой
сегмент и `a/b`), поэтому до обработчика не доходят и путь задания из них
не строится.
Пока песочница работает, маршрут читает каталог задания одной короткой
командой и отдаёт хвост каждого потока не больше 64 КиБ, размеры файлов,
код выхода и `source: "sandbox"`. Остановленную, заархивированную или
удалённую песочницу он не будит: незавершённое задание становится
`interrupted`, завершённое отдаётся из базы с `source: "saved"`. Daytona
недоступна, ключ удалён или песочница отмечена `gone` — `503`. Ответ
кэшируется в процессе на секунду, поэтому несколько открытых вкладок не
нагружают Daytona.

Карточка опрашивает маршрут сразу при показе, затем раз в 2 секунды; через
минуту — раз в 5 секунд, через десять минут — раз в 10 секунд. При скрытой
вкладке опрос останавливается и возобновляется при возвращении. Ошибки
сети и `5xx` повторяются с удвоением задержки от 2 до 30 секунд; после пяти
ошибок под выводом написано «Нет связи, повторяем…». `401` и `404`
останавливают опрос. Вывод заменяется хвостом из песочницы и прокручивается
вниз, пока пользователь не прокрутил его вверх.

«Стоп» отменяет только текущий ход. Приложение не останавливает песочницу и
не убивает процессы: команда, уже ушедшая в фон, продолжает работу, а
карточка продолжает опрос. Это же поведение работает при открытии старой
сессии и после завершения хода. Задание с кодом 143 (его остановила модель
через `kill`) показывается завершённым, а не прерванным.

## Копии агента

Агент запускает копию себя инструментом `agent` (`agent/tools/agent.ts`). Копия
получает те же инструкции, инструменты и песочницу, но не видит историю
беседы: всё нужное передаётся в `message`. Копии берут на себя независимые
части работы, которые пишут в разные файлы; одновременно работает не больше
32 задач.

Карточка вызова показывает состояние копии: «Запускается…», текущее действие
(«Сейчас: …»), «Ждёт ответа», начало итога, ошибку или остановку. Нажатие на
карточку открывает боковую панель с ходом копии. На компьютере панель не
затемняет чат и не блокирует его — лента освобождает 480 пикселей справа, а
панель закрывается кнопкой и Escape; на телефоне она занимает весь экран.
Ход копии читается из её собственного потока (`useEveAgent({ followSubagents:
true })`), а файлы песочницы в нём выводятся текстом пути: файлы показывает
корневой агент.

Поток копии в `session_events` не сохраняется — он живёт в eve, пока жива
сессия копии, а сессии не истекают по простою (`limits.sessionTimeoutMs:
false`). Поэтому после перезагрузки страницы карточки показывают итоги, а
панель — ход копии или «Ход копии недоступен», если eve уже не отдаёт поток.

### Владелец потока копии

eve не проверяет, чья сессия стоит в адресе `/eve/v1/session/:id`, поэтому
владельца проверяет канал. Строку `agent_sessions` (`app_session_id`,
`eve_session_id`, `task_id`, `call_id`, `name`) синхронизатор событий создаёт
вместе с событием `agent.started`. Решения проверяются по порядку: корневая
сессия пользователя — обычные правила сессии; копия пользователя — только
`GET …/stream` (сообщения, `cancel`, `clear`, `compact`, `reset` копии отвечают
403 `session_forbidden`, потому что ломают задачу корня); известная чужая
сессия — 403 сразу; неизвестный идентификатор потока ждёт строку копии до
трёх секунд, если у пользователя была активность за последние пять минут, и
только потом отказывает.

Строка копии появляется через 39–211 мс после `agent.started` в потоке корня,
включая публикацию по завершении шага модели родителя: это меньше
трёхсекундного ожидания, и поток копии открывается без отказа. Открытие
страницы сессии с десятью прошлыми копиями — это десять запросов потоков, по
одному на копию (каждый поток закрывается, догнав копию), и три обращения к
базе на запрос в аутентификаторе: сессия входа, строка корня, строка копии.
Отметка `auth_sessions.last_seen_at` обновляется не чаще раза в пять минут.

## Файлы в ответе агента

Агент показывает файл ссылкой без схемы: `[ролик](out/final.mp4)` или
`![кадр](out/cover.png)`. Относительные пути считаются от `/workspace`;
`?query` и `#fragment` отбрасываются, процентное кодирование раскрывается один
раз. Файлом считается только путь строго внутри `/workspace/`: `/etc/passwd`,
`../x`, `%2e%2e/x`, обратная косая черта и управляющие символы отвергаются, а
`realpath` в песочнице проверяет, что символическая ссылка не ведёт наружу.
Обычные адреса (`https:`, `mailto:`, `data:`, `file:`) остаются ссылками.

При завершении текстового блока сообщения хук `agent/hooks/message-files.ts`
копирует найденные файлы в S3 под ключом
`u/<user_id>/s/<app_session_id>/message-files/<uuid>/<имя>`: ход он задерживает
не дольше 30 секунд, а не успевший файл доделывается в фоне. Копия нужна, чтобы
старые сообщения работали без песочницы и не менялись при перезаписи файла
агентом. Строка `message_files` хранит состояние `copying`, `ready` или
`missing` с причиной (`not_found`, `outside_workspace`, `too_large`,
`too_many`, `copy_failed`); на сообщение принимается не больше 20 уникальных
ссылок. Предел размера задаёт `MEDIA_COPY_MAX_BYTES` (по умолчанию 2 ГиБ).

- `GET /api/sessions/:id/files` — файлы всех сообщений сессии для страницы чата.
- `GET /api/media/:id` — `302` на подписанную ссылку S3 на 15 минут; чужая и
  несуществующая запись — `404`. `?download=1`, `text/html` и `application/pdf`
  приходят как вложение; видео, аудио и изображения — встроенно.

В браузере общий с сервером разбор `lib/media/sandbox-path.ts` подключён к
Streamdown remark-плагином до `remark-rehype`: файл получает адрес
`/__sandbox-file/<путь>`, отвергнутый — `/__sandbox-file-rejected`. Компоненты
`a` и `img` рисуют скелет, плеер, изображение или карточку скачивания, а
остальные адреса отдают штатному обработчику Streamdown. `rehype-harden`
пропускает адреса файлов песочницы и блокирует удалённые изображения. В режиме
копии агента (#12) файлы не разрешаются: выводится путь текстом.

Видео, скопированное в S3, играет в чате и после остановки песочницы и
перезагрузки страницы. Копирование файла 500 МБ не укладывается в 30-секундный
бюджет хука: ход продолжается, файл докачивается в фоне, а `session.waiting`
приходит после завершения копирования — десятки секунд при скорости хранилища
около 2 МБ/с. Файл не читается в память целиком: рост `rss` процесса eve при
копировании — единицы процентов от размера файла.

## Загрузка файлов пользователя

Пользователь прикладывает файл скрепкой, перетаскиванием на беседу или вставкой
из буфера обмена. Браузер сразу просит у сервера строку `media` и подписанную
ссылку (`POST /api/uploads`) и кладёт файл прямо в S3: тело файла через сервер
приложения не идёт. `Content-Type` входит в подпись, поэтому `PUT` с другим
типом хранилище отвергает, а ссылка живёт 15 минут. Предел одного файла задаёт
`UPLOAD_MAX_BYTES` (по умолчанию 256 МиБ, не больше 5 ГБ), одного сообщения —
10 файлов и 4 ГиБ; одновременно загружаются не больше трёх файлов.
Изображение из буфера без имени называется «Снимок экрана ГГГГ-ММ-ДД ЧЧ-ММ-СС.png».

Файл доходит до агента вложением: eve забирает байты из S3 по адресу
`/api/media/<uuid>` (чужие адреса не скачивает) и кладёт в песочницу под
`/workspace/.eve/attachments/<хеш>/<имя>`, а модели показывает подпись с путём.
В ленте у сообщения видны имя и миниатюра изображения, размер — только в
предпросмотре под полем ввода. Пока идёт загрузка или у файла ошибка, отправка
недоступна: у ошибки есть «Повторить» и «Убрать».

### CORS бакета

Подписанная ссылка строится на `S3_ENDPOINT`, поэтому этот адрес должен быть
доступен браузеру пользователя, а у бакета нужно правило CORS: источник
`APP_URL`, метод `PUT`, разрешённый заголовок `Content-Type`. Для хранилища из
`compose.yaml` (`pgsty/silo`) настраивать ничего не нужно: `MINIO_API_CORS_ALLOW_ORIGIN`
по умолчанию `*`. Ссылка проверяется хранилищем при начале загрузки; заявленный
размер сверяет уже eve при доставке файла агенту.

### Пределы и память

`fetchFile` канала возвращает байты одним `Buffer`: потоковой передачи у eve нет,
поэтому файл целиком живёт в памяти процесса, а пик примерно в пять раз больше
размера файла (копии при чтении из S3, проверке типа и записи в песочницу).
Поэтому предел одного файла по умолчанию — 256 МиБ; на сервере с запасом памяти
его можно поднять переменной `UPLOAD_MAX_BYTES`.

Сбой записи в песочницу (например, кончилось место) eve не превращает в заметку
для модели: ошибка записи не перехватывается в `attachment-staging`, ход
завершается ошибкой и пользователь видит общее «Не удалось получить ответ».

## Вход через Telegram

Отдельных учётных записей нет: пользователь входит через Telegram, при первом входе
создаётся строка `users`. Вход использует Telegram OpenID Connect: браузер
переходит на страницу Telegram, сервер обменивает код на `id_token` и проверяет его.

1. Создайте бота в [@BotFather](https://t.me/botfather) и откройте у него **Login Widget**.
2. Если показана **Switch to OpenID Connect Login**, включите этот режим:
   он навсегда отключает старый Login Widget у этого бота.
3. Зарегистрируйте публичный HTTPS-адрес приложения (`APP_URL`):
   - **Trusted Origins**: `<APP_URL>`;
   - **Redirect URIs**: `<APP_URL>/api/auth/telegram/callback`.

   В интерфейсе с общим списком **Allowed URLs** добавьте оба адреса туда.
   `localhost` BotFather не принимает: для локальной проверки используйте HTTPS-туннель.
4. Скопируйте **Client ID** и **Client Secret** в `TELEGRAM_CLIENT_ID` и
   `TELEGRAM_CLIENT_SECRET`. Client Secret — отдельное значение, не токен бота;
   он хранится только на сервере.
5. Не меняйте алгоритм подписи `id_token`: сервер проверяет `RS256`.
6. Задайте `SESSION_SECRET` длиной не короче 32 символов:
   `openssl rand -base64 48`.

Поток: `GET /api/auth/telegram/login` создаёт `state`, одноразовый `nonce` и PKCE,
сохраняет их в подписанной HttpOnly-cookie на 10 минут и направляет в Telegram.
`GET /api/auth/telegram/callback` проверяет cookie и `state`, обменивает код,
проверяет подпись по JWKS, `iss`, `aud`, `exp`, `iat`, `sub` и `nonce`,
гасит nonce и создаёт сессию. Временная cookie удаляется и при успехе, и при отказе.

Для локальной разработки без Telegram включите `DEV_LOGIN_ENABLED=1` (только
`localhost`, `127.0.0.1` или `[::1]`) и откройте
`/api/auth/dev-login?telegramId=777&name=Разработчик`. Параметр `operator=1`
делает пользователя оператором.

`GET /eve/v1/health` публичен; остальные маршруты eve требуют cookie сессии,
а `GET /eve/v1/info` доступен только оператору.

## Команды

| Команда | Что делает |
| --- | --- |
| `npm run dev` | разработка (`next dev`) |
| `npm run build` | сборка: `eve build` и `next build` |
| `npm start` | production-запуск (сначала нужен `npm run build`) |
| `npm run db:generate` | создать миграцию из изменений схемы |
| `npm run db:migrate` | применить миграции к базе из `DATABASE_URL` |
| `npm run daytona:add-key -- <метка>` | зашифровать и добавить ключ Daytona из stdin |
| `npm run test:http` | HTTP-тесты запущенного приложения |
| `npm run test:render` | тесты отрисовки в настоящем Chromium |

`npm run build` секретов не требует: проверка переменных окружения
пропускается на фазе сборки. При `npm start` сначала выполняйте
`npm run build` — он делает `eve build`, и eve при этом слушает порт `4274`
(`EVE_NEXT_PRODUCTION_PORT`).

## Тесты

```bash
docker compose up -d
npm run test:http
```

Тесты запускают настоящее приложение и ходят в него по HTTP: глобальная
подготовка создаёт базу `*_test`, бакет, применяет миграции и поднимает
основной экземпляр `next dev` на `TEST_APP_PORT`, отдельные тесты поднимают
свои экземпляры через `startApp()`. Работать тесты могут только с базой,
имя которой оканчивается на `_test`.

При `APP_TEST_MODE=1` внешний SDK Daytona заменён файловой фиктивной песочницей,
но провайдер, шифрование, выбор ключа и база остаются настоящими. Общий каталог
`FAKE_SANDBOX_DIR` (в `.env.test`: `.tmp/fake-sandbox`) видят приложение, eve и
тесты. Он автоматически очищается перед каждым тестовым файлом. Помощник
`fakeSandbox` задаёт файлы, правила команд и отказы, имитирует автостоп,
показывает вызовы и счётчики. Команды на компьютере тестировщика не исполняются.
Квота ключа задаётся `fakeSandbox.setQuota(apiKey, {cpu, memoryGb, diskGb})`
(по умолчанию 10/10/30), общая организация двух ключей — `setOrganization`,
отказ использования — `failUsage(apiKey, "forbidden" | "unavailable" |
"unauthorized" | "unexpected")`, архивация — `archive(appSessionId)`. `usageCalls(apiKey)`
считает запросы использования, а `counters()` показывает `created` и
`createAttempts` (включая отказ по квоте). Фиктивные `/api-keys/current` и
`/organizations/{id}/usage` отвечают в форме настоящего Daytona с несколькими
`regionUsage`, включая `linux-vm` и служебный регион `earth`; создание сверх
квоты отказывает так же, как Daytona.
Сложный служебный скрипт `bash` проверяется через штатные stubs eve;
`read_file` и `edit_file` обращаются к настоящему провайдеру с фиктивным
внешним слоем. Встроенного `write_file` нет: правки идут через `edit_file`
(лимит 256 КиБ, точная замена UTF-8; полный выход с `oldContent`/`newContent`
попадает в поток и `session_events`, модели — короткий текст без содержимого).
Если шаг eve прервался и инструмент выполнился повторно, уже применённая
замена даёт `fragment_not_found` — это принято. Пакет `just-bash` нужен
только встроенному dev-помощнику eve, который готовит свою отдельную среду;
приложение его вместо Daytona не выбирает.

Два `next dev` на один проект не мешают друг другу: каждый экземпляр получает
свой `NEXT_DIST_DIR` (`.next-test-<порт>`), поэтому блокировка `.next/dev/lock`
не конфликтует. При этом `withEve()` держит один dev-сервер eve на корень
проекта (состояние в `.eve/`) — второй экземпляр делит процесс eve с первым,
изоляции окружения eve нет. Тестам, которым нужно другое окружение eve,
понадобится остановить основной экземпляр и вынести их в отдельные файлы.

### Тесты отрисовки

```bash
npx playwright install chromium   # один раз: браузер для Vitest Browser Mode
npm run test:render
```

Тесты открывают настоящий Chromium (безголовый) и проверяют интерфейс в окнах
390×844 и 1280×800. База и Docker для них не нужны.

На EndeavourOS установщик Playwright предупреждает, что система не
поддерживается официально, и ставит сборку для Ubuntu. Если Chromium не
запускается из-за нехватки системных библиотек, `npx playwright install-deps`
не поможет: он вызывает `apt-get`, которого на EndeavourOS нет. Посмотреть
недостающие библиотеки:

```bash
ldd ~/.cache/ms-playwright/chromium_headless_shell-*/chrome-headless-shell-linux64/chrome-headless-shell | grep "not found"
```

и поставить их через pacman, например:

```bash
sudo pacman -S --needed alsa-lib at-spi2-core dbus expat glib2 libdrm libxkbcommon \
  libxcomposite libxdamage libxfixes libxrandr mesa nspr nss
```
