# 42 AI Studio

Сайт для создания видео с помощью ИИ. Пользователь ставит задачу, агент-видеограф
собирает Remotion-композицию, озвучивает, рендерит и отдаёт готовый ролик.

## Создание и правки ролика

Опишите тему, аудиторию, длительность и формат кадра; укажите, нужны ли
озвучка и музыка, прикрепите свои материалы. Если существенного не хватает,
агент задаст до трёх вопросов и дождётся ответа. Остальные параметры берёт
по умолчанию: 16:9, 1920×1080, 30 к/с, 30 секунд, язык просьбы.

Перед работой агент показывает короткий план сцен. Он создаёт motion-графику
кодом Remotion, проверяет 4–8 опорных кадров и исправляет найденные дефекты
до полного рендера. Просмотренные изображения появляются в чате как карточки
«Кадр»: миниатюру можно открыть крупно. Кадры сохраняются в S3 и остаются
доступны после остановки песочницы; при сбое сохранения показано «Кадр недоступен»,
а просмотр модели не прерывается.

Готовое видео появляется прямо в беседе. Для правки напишите, что изменить:
агент продолжит тот же проект, перепроверит затронутые сцены и пришлёт отдельный
файл с суффиксом `-v2`, сохранив предыдущий. Структура сцен и проверки хранятся
в `NOTES.md` проекта. После трёх неудачных попыток агент упрощает композицию
и прямо сообщает об отличиях; непроверенный результат не считается готовым.

## Запуск с нуля

Нужен Node.js 24.15.0 или новее в ветке 24.x. Закреплённый `jsdom` 30.1.3
объявляет поддержку `^22.22.2 || ^24.15.0 || >=26.0.0`; проект использует 24.x.

```bash
cp .env.example .env        # значения-заглушки, секретов в образце нет
docker compose up -d        # Postgres и хранилище, бакеты studio-dev и studio-test
npm install
npm run db:migrate          # применяет миграции к базе из DATABASE_URL
npm run dev
```

Проверить, что всё поднялось:

```bash
curl -i http://localhost:3000/api/health     # {"status":"ok","checks":{"database":"ok","storage":"ok"}}
curl -i http://localhost:3000/eve/v1/health  # {"ok":true,...}
```

`GET /api/health` отвечает `503`, если недоступна база или хранилище; тексты
ошибок при этом уходят только в журнал сервера.

### Как вручную увидеть отказ хранилища

```bash
S3_ENDPOINT=http://localhost:1 npm run dev
curl -i http://localhost:3000/api/health
# {"status":"error","checks":{"database":"ok","storage":"error"}}
```

## Состояние eve

Каталог `.eve/.workflow-data` хранит состояние запусков eve (сессии, потоки,
очереди). Это требование eve: в рабочей среде каталог должен лежать на
постоянном диске и переживать перезапуск процесса, иначе durable-сессии и
идущие ходы теряются. В разработке он создаётся сам.

Не запускайте `npm run dev` и `npm run test:http` одновременно: `withEve()`
держит один dev-сервер eve на корень проекта, и экземпляр тестов делит его с
разработкой — проверки входа в тестах начинают отвечать 401. Остановите один
из процессов перед запуском другого.

## Модель агента

Модель задаётся переменными `AGENT_MODEL` и `AGENT_REASONING`; без
`AGENT_MODEL` (и без `APP_TEST_MODE=1`) сервер не стартует. Для
OpenAI-совместимого провайдера задайте `AGENT_MODEL_BASE_URL`,
`AGENT_MODEL_API_KEY` и `AGENT_MODEL_CONTEXT_TOKENS`; для AI Gateway достаточно
`AGENT_MODEL` и ключа `AI_GATEWAY_API_KEY`, который читает сам AI SDK.
`AGENT_MODEL_API=anthropic` вызывает Messages API того же адреса (`<url>/messages`),
если модель не принимает Chat Completions.

По умолчанию используется поток провайдера. Если OpenAI-совместимый API
корректно возвращает вызовы инструментов только в обычном ответе, задайте
`AGENT_MODEL_STREAMING=false`. Штатный адаптер AI SDK сохраняет инструменты,
рассуждение и учёт токенов; приложение по-прежнему получает события eve,
но текст каждого шага появляется после получения полного ответа API.

## Песочница Daytona

Задайте `SECRETS_ENCRYPTION_KEY` в `.env`: результат `openssl rand -base64 32`.
Храните его отдельно от базы и сохраняйте при переносе приложения: смена ключа
без перешифрования делает сохранённые секреты нечитаемыми. Сервер проверяет
строгий base64 и длину 32 байта при запуске; сборке секреты не нужны.

После миграций добавьте API-ключ Daytona через стандартный ввод из защищённого
файла (не вставляйте секрет в аргументы команды):

```bash
npm run daytona:add-key -- основной < /путь/к/файлу-с-ключом
```

В базе остаётся только AES-256-GCM-шифротекст. Команда печатает идентификатор
записи и права ключа. Ключи образуют пул: новая песочница создаётся на ключе
со свободной квотой, а отключение ключа не мешает восстановлению уже созданной
песочницы. Если второй ключ той же организации уже есть, команда предупреждает,
что они делят одну квоту.

`DAYTONA_API_URL` задаёт API, `SANDBOX_CPU`, `SANDBOX_MEMORY_GB` и
`SANDBOX_DISK_GB` — ресурсы (по умолчанию 2 vCPU, 4 GiB, 8 GiB).
Песочница создаётся из `agent/sandbox/Dockerfile`, автоматически останавливается
через `SANDBOX_IDLE_STOP_MINUTES` минут бездействия (по умолчанию 15) и
архивируется после `SANDBOX_ARCHIVE_AFTER_DAYS` суток остановки (по умолчанию 7).
Автоудаление выключено. Следующее обращение восстанавливает ту же файловую систему.
Песочницы приложения помечены меткой `studio_session` с идентификатором сессии;
остановленная машина продолжает занимать дисковую квоту, а архивная освобождает её; поэтому
после ручных прогонов их удаляют командой
`npm run daytona:cleanup -- <appSessionId>` (или `-- --all`). Команда обходит
все ключи пула: ключ Daytona видит только свою организацию. Удаление строки
`sandboxes` или пользователя машину в Daytona не удаляет.

### Ключи Daytona

Квота принадлежит организации Daytona, а не ключу: несколько ключей одной
организации делят одно место. В `daytona_keys` лежат шифротексты, `usage` —
последнее прочитанное использование, `usage_checked_at` — время последней
попытки, `exhausted_until` — до какого времени пул считается исчерпанным.

Форма `usage`, которую читает админка:

```json
{
  "source": "daytona",
  "fetchedAt": "2026-11-04T19:38:35.751Z",
  "organizationId": "organization-id",
  "region": "eu",
  "cpu": { "used": 6, "quota": 10 },
  "memoryGb": { "used": 9, "quota": 10 },
  "diskGb": { "used": 30, "quota": 30 },
  "maxPerSandbox": null,
  "error": null
}
```

`source` — `daytona` или `error`; `fetchedAt` — последнее успешное чтение;
`cpu`, `memoryGb`, `diskGb` — `{used, quota}` в vCPU и ГиБ; `maxPerSandbox` —
пределы на одну песочницу или `null`; `error` — `unauthorized`, `forbidden`,
`unavailable`, `unexpected` или `null`. При ошибке прежние числа сохраняются,
`error` заполняется, а `usage_checked_at` сдвигается. Ответ Daytona, тексты
исключений и значение ключа в базу и журнал не попадают.

Правила выбора:

- Включённые неудалённые ключи перебираются по `created_at`, затем `id`.
- Использование моложе 30 секунд не перечитывается. `usage` помнит
  `organizationId`; если `GET /api-keys/current` его не вернул, берётся
  единственная организация из `GET /organizations`, иначе `organizationId`
  любой песочницы этого ключа. Когда организацию определить нельзя, в `usage`
  пишется `unexpected`, и ключ не блокируется.
- Из `regionUsage` берутся записи `container` (не `linux-vm` и не `windows`)
  и не из служебного региона `earth`; при нескольких подходящих — регион по
  умолчанию организации (`defaultRegionId`). Единицы — vCPU, ГиБ памяти,
  ГиБ диска.
- Ключ подходит, если `quota - used - reserved >= need` по всем измерениям.
  `reserved` — строки `sandboxes` в `starting` моложе 5 минут: создание
  резервирует vCPU, память и диск, пробуждение остановленной — только vCPU и
  память (диск уже занят ею), восстановление из архива — всё.
- Ключи одной организации — один пул, представитель — ключ с наименьшим
  `created_at`. Исчерпанный пул пропускается целиком.
- `unauthorized` исключает ключ из выбора. `forbidden`, `unavailable` и
  `unexpected` без прежних чисел выбор не останавливают.
- Если Daytona отказала при создании по квоте (`400` и сообщение
  «Total … limit exceeded»), пул помечается исчерпанным на 60 секунд, и выбор
  переходит к следующему ключу; `401` исключает ключ. Любой другой `400` даёт
  `sandbox_create_failed`.
- Нет ни одного включённого неудалённого ключа — `no_daytona_key`; ключи есть,
  но места нет — выбор ключа возвращает нехватку ёмкости, а провайдер ждёт в очереди.

Остановленная контейнерная песочница занимает диск до архивации, поэтому на
Tier 1 при диске 8 ГиБ неархивных песочниц не больше трёх. Отключение
(`enabled = false`) не мешает просыпаться уже созданным песочницам, но новые
на ключе не создаются. Удаление (`deleteKey`) ставит `deleted_at`, отключает
ключ и удаляет его песочницы; шифротекст заменяется маркером `deleted` только
когда удалить удалось все машины. Если часть не удалилась, её идентификаторы
сохраняются отдельно, шифротекст остаётся, и операцию можно повторить даже
после того, как сессия перешла на другую песочницу. Переписка, события и
файлы остаются в базе и S3; следующее сообщение сессии создаёт новую пустую песочницу на
другом ключе.

Ключ Daytona принадлежит одной организации. `GET /api-keys/current` отдаёт
`organizationId` необязательным полем; `GET /organizations` перечисляет
организации владельца ключа, а не самого ключа, поэтому при нескольких
организациях нужен `organizationId` песочницы. Запрос
`GET /organizations/{id}/usage` принимает ключ с правом `read:billing` или
`write:sandboxes`; для создания и удаления песочниц достаточно
`write:sandboxes` и `delete:sandboxes` (чтение песочниц выдаётся всегда).
Документация Daytona расходится по памяти Tier 1 (10 и 20 ГиБ в разных
таблицах), поэтому числа не зашиты, а читаются из ответа использования.

### Очередь песочниц

У пользователя не больше одной запускающейся или запущенной песочницы. При
обращении из другой сессии свободная первая песочница останавливается сразу;
если первая занята, вторая ждёт. Занятой считается сессия с открытым ходом,
кроме явного ожидания ответа пользователя (`turn.waiting` с `on: "input"`).
После ответа (`input.resolved` или `step.started`) тот же ход снова занят.
Занятость учитывается отдельно для каждой копии общей песочницы: вопрос одной
не позволяет остановить машину, пока другая работает. Переключение возможно,
когда все участники закончили работу или ждут ответа пользователя.
Завершение или отмена хода освобождает сессию немедленно. Свежая неполная
история событий защищает её ещё две минуты. Живая фоновая команда также
считается работой: диспетчер читает каталог задания, но не дольше шести часов
с создания его записи. Ошибка чтения не означает, что процесс завершился.

При нехватке места заявки обслуживаются по времени поступления. Если старшей
не хватает квоты на её ключе, следующие могут получить место на другом.
Диспетчер останавливает чужие песочницы только после порога простоя и никогда
не вытесняет занятые. Остановка освобождает vCPU и память, но не диск. Когда
не хватает только диска для создания или восстановления, архивируется самая
давно остановленная свободная песочница того же пула, не принадлежащая заявителю.
Слот после завершения хода сохраняется до порога простоя, если его не запросила
другая сессия этого пользователя.

Очередь движется внутри ожидающих вызовов, без отдельного фонового сервиса.
Пока есть ожидающие, состояния и квоты сверяются с Daytona, а занятым
запущенным песочницам продлевается нативная активность (`refreshActivity`).
**При пустой очереди диспетчер не работает:** нативный автостоп Daytona может
остановить песочницу и убить фоновую команду, если за порог простоя не было
обращений к toolbox. Работа процесса сама таймер не сбрасывает; открытая
карточка фоновой команды поддерживает активность своим опросом.

`SANDBOX_IDLE_STOP_MINUTES` принимает целое 1–1440, `SANDBOX_ARCHIVE_AFTER_DAYS` —
1–30. При пробуждении и восстановлении интервалы выставляются заново, поэтому
смена настроек применяется и к старым машинам. `SANDBOX_QUEUE_MAX_WAIT_SECONDS`
ограничивает ожидание (5–14400 секунд, по умолчанию 1800), а
`SANDBOX_QUEUE_POLL_MS` задаёт период проверки (100–10000 мс, по умолчанию 2000).
После предельного ожидания инструмент сообщает `sandbox_queue_timeout`; новое
сообщение может повторить попытку. «Стоп» снимает заявку и завершает ожидание
с `sandbox_wait_cancelled`, не мешая следующему ходу.
Отмена действует и до появления заявки: запоздавший ответ Daytona и повтор
старого шага не возобновляют ожидание. Уже отправленный запрос запуска может
завершиться в Daytona; его результат сохраняется для последующего обращения,
но отменённый ход не получает подключение и не ставится в очередь заново.

`GET /api/sessions/:id/sandbox` доступен только владельцу, не будит песочницу и
возвращает `state` (`none`, `queued`, `starting`, `started`, `stopped`, `archived`)
и `queue` (`null` либо `{position, total, reason}`). Причина — `capacity` или
`own_session_busy`; позиция считается только среди заявок с heartbeat моложе
минуты. Чат показывает очередь и запуск над полем ввода и обновляет состояние
раз в три секунды, пока идёт ход или виден баннер. Поле ввода остаётся активным.

Контрольные времена для 4 vCPU / 4 ГиБ / 8 ГиБ: пробуждение остановленной
песочницы — 4,1 с, восстановление архивной — 15,5 с; файлы сохранились.
Время включает очередь, запуск и обновление интервалов. Таймаут `start(300)`
составляет 300 секунд и оставляет запас для восстановления; это не гарантия
постоянной задержки сервиса. При пороге простоя в одну минуту нативная остановка
началась через 67,5 с и завершилась через 83,2 с; фоновая группа процессов
погибла без обращений к toolbox.

Команды работают от root. Образ `agent/sandbox/Dockerfile` содержит Python 3.12 с Pillow,
Node 24, библиотеки Chrome, шрифты с кириллицей и эмодзи и шаблон Remotion
4.0.538 в `/opt/remotion`. Chrome Headless Shell ставится при сборке командой
`npx remotion browser ensure` и лежит в `/opt/remotion/node_modules/.remotion`.
В образ входят `sandbox-vcpu` (число vCPU по квоте cgroup) и `sandbox-selfcheck`
(версии Node, Python и Remotion, запуск браузера, русский шрифт, один кадр
композиции `Main`). Новый проект собирается копированием шаблона и ссылкой
`node_modules` на `/opt/remotion/node_modules`.

Документацию и страницы агент читает инструментом `read_page` на сервере
приложения: песочница до обычных сайтов не ходит. Поиск — `web_search` через
Tavily (`TAVILY_API_KEY`, необязательный `TAVILY_API_URL`). Без ключа сервер
стартует, а поиск сообщает, что он не настроен; имена страниц Remotion тогда
берутся из `https://www.remotion.dev/llms.txt`. Адреса внутренней сети,
служебные IP и ссылки с логином `read_page` не открывает.

Навыки Remotion ставятся из того же тега, что и `ARG REMOTION_VERSION`:

```bash
npx skills add https://github.com/remotion-dev/remotion/tree/v4.0.538/packages/skills --skill remotion-create remotion-docs remotion-markup remotion-multimedia remotion-render remotion-captions remotion-interactivity --subagent root -y
```

Образ проверяется созданием песочницы и командой `sandbox-selfcheck`:

```bash
daytona create --dockerfile agent/sandbox/Dockerfile --cpu 2 --memory 4 --name studio-image-check
```

`--memory` задаётся в гигабайтах. Повторное создание берёт кэш декларативного
образа: Daytona держит его на раннере 24 часа.

При сборке `prepare` собирает workspace и навыки в JSON-артефакт через
`ctx.populate`, без Daytona и базы. При создании песочницы файлы доставляются
одним пакетом: `workspace/` → `/workspace`, навыки с вложенными файлами →
`$HOME/.agents/skills`. `$HOME` определяется внутри живой песочницы.
Изменение начальных файлов влияет только на новые песочницы.

На тарифах Tier 1/2 доступны только сервисы белого списка Daytona, в том числе
npm, PyPI, GitHub и Hugging Face. Произвольные сайты и YouTube из песочницы
недоступны; настройка отдельной песочницы это ограничение не снимает.
Фоновый процесс сам по себе не сбрасывает таймер автостопа.

Песочница работает от `root`; память и CPU соответствуют `SANDBOX_MEMORY_GB` и
`SANDBOX_CPU`. Многострочные скрипты сохраняют кавычки, heredoc и `$(…)`.
Фоновый процесс переживает конец хода. После внешней остановки следующее
сообщение восстанавливает ту же песочницу с файлами в `/workspace` и `/tmp`.
В Daytona на сессию приходится одна песочница. Неверный ключ даёт
`sandbox_create_failed` с русским сообщением без значения ключа.

## Поиск и чтение страниц

`web_search` ищет через Tavily, `read_page` загружает страницу напрямую с сервера
приложения, без Tavily Extract. Поисковый запрос передаётся Tavily; адрес страницы
при чтении — только её сайту. Содержимое источников считается чужими данными,
а не инструкциями для агента.

Зарегистрируйтесь в [Tavily](https://app.tavily.com), скопируйте API-ключ в `.env`.
Бесплатный тариф даёт 1000 кредитов в месяц без банковской карты. Поиск `basic`
стоит 1 кредит, `advanced` — 2. При оплате по использованию кредит стоит $0.008:
один поиск — $0.008 или $0.016 соответственно; актуальные тарифы — в
[документации Tavily](https://docs.tavily.com/documentation/api-credits).

| Переменная | Настройка |
| --- | --- |
| `TAVILY_API_KEY` | Серверный ключ из кабинета Tavily. Необязателен: без него приложение запускается, но поиск сообщает, что не настроен. Передаётся API через `Authorization: Bearer`, не включается в ответы и журналы |
| `TAVILY_API_URL` | По умолчанию `https://api.tavily.com`, без завершающего `/`. Вне `APP_TEST_MODE=1` обязателен HTTPS. Для тестового сервера в `.env.test` — `http://127.0.0.1:59102` |

### Возможности и ограничения чтения

- Принимаются HTTP/HTTPS-ссылки до 2000 знаков, без логина и пароля, только
  порт 80 для HTTP и 443 для HTTPS. Куки, `Authorization` и `Referer` пользователя
  не отправляются, TLS-сертификаты проверяются.
- Общий срок вызова — 30 секунд, соединения — до 10 секунд; отмена хода
  прекращает загрузку и разбор. Размер ответа после распаковки — до 5 МиБ.
- HTML/XHTML переводится в Markdown в отдельном потоке `worker_threads`.
  `extract: "auto"` выделяет статью; если её нет или текст короче 500 знаков,
  используется вся страница. `extract: "page"` сохраняет меню и навигацию.
  При более чем 20 000 DOM-элементов выделение статьи пропускается. HTML
  больше 2 МиБ разбирается только по первым 2 МиБ в режиме `page`.
- Скрипты и загрузка ресурсов отключены. Страницы, строящие содержимое
  JavaScript, страницы за входом и антибот-защитой могут быть недоступны;
  браузерного рендеринга и обхода ограничений доступа нет. PDF, изображения,
  видео и архивы инструмент не читает.
- Markdown, обычный текст, CSV, JSON, XML, RSS и Atom возвращаются как текст
  (`extraction: "raw"`). Кодировка определяется по BOM, затем HTTP-заголовку,
  затем HTML meta в первых 4 КиБ; запасной вариант — UTF-8. Поддерживаются,
  в частности, windows-1251 и KOI8-R.
- За вызов возвращается до 20 000 единиц UTF-16 по умолчанию (`maxChars` —
  от 1000 до 40 000). Для продолжения передайте `nextOffset` как `offset`,
  не вычисляя его самостоятельно. Разобранный текст кэшируется на 10 минут,
  не больше 20 страниц; после вытеснения или перезапуска страница загружается
  заново. Текст короче 50 знаков считается пустой страницей.

Документация Remotion читается по `https://www.remotion.dev/docs/<страница>.md`,
например `https://www.remotion.dev/docs/sequence.md`; путеводитель —
`https://www.remotion.dev/llms.txt`. Если Markdown-адрес отвечает 404, агент
может прочитать адрес без `.md`. При 404 загрузчик также один раз повторяет
запрос, отдавая в `Accept` предпочтение HTML вместо Markdown, в пределах того
же общего срока.

### Защита от обращений во внутреннюю сеть (SSRF)

Все запросы к пользовательским адресам проходят общий `lib/web/safe-fetch.ts`.
URL нормализуется стандартным парсером: альтернативные записи IPv4 приводятся
к обычному адресу, IDN — к punycode, конечная точка имени при проверке
отбрасывается. Схемы, кроме HTTP/HTTPS, ссылки с учётными данными и порт 0
отвергаются. Имя и IP проверяются раньше порта.

| Имена узлов | Запрещено |
| --- | --- |
| Локальные имена | `localhost`, имена без точки, суффиксы `.localhost`, `.local`, `.localdomain`, `.internal`, `.intranet`, `.lan`, `.home.arpa`, `.corp`, `.home` |

| Семейство | Запрещено |
| --- | --- |
| IPv4 | `0.0.0.0/8`, `10.0.0.0/8`, `100.64.0.0/10` (CGNAT), `127.0.0.0/8`, `169.254.0.0/16` (в том числе метаданные облака `169.254.169.254`), `172.16.0.0/12`, `192.0.0.0/24`, `192.0.2.0/24`, `192.88.99.0/24`, `192.168.0.0/16`, `198.18.0.0/15`, `198.51.100.0/24`, `203.0.113.0/24`, `224.0.0.0/4`, `240.0.0.0/4` (включая `255.255.255.255`) |
| IPv6 | Разрешены только глобальные одноадресные `2000::/3`, из них запрещены `2001::/23`, `2001:db8::/32`, `2002::/16` (6to4), `3fff::/20`; всё остальное запрещено целиком: `::`, `::1`, `::/96`, **`::ffff:0:0/96` (отображённые IPv4) в любой записи, десятичной и шестнадцатеричной**, `64:ff9b::/96`, `64:ff9b:1::/48`, `100::/64`, `5f00::/16`, `fc00::/7`, `fe80::/10`, `fec0::/10`, `ff00::/8` |

Публичные IP-литералы разрешены, отображённые IPv4 в IPv6 — нет. Проверяются
все ответы DNS: один запрещённый IP блокирует всё имя. Проверка повторяется
непосредственно при соединении через `connect.lookup`, чтобы исключить подмену
DNS между предварительной проверкой и подключением. Отдельные списки IPv4 и
IPv6 не позволяют правилу отображённых адресов ошибочно блокировать весь IPv4.
Исключения `allowHosts` и подмена DNS `resolveDns` передаются только тестами;
переменной окружения для отключения защиты чтения нет.

| Перенаправления `read_page` | Правило |
| --- | --- |
| Коды и предел | Вручную обрабатываются 301, 302, 303, 307, 308; разрешено не больше пяти переходов, шестой — ошибка |
| Адрес назначения | Относительный `Location` разрешается от текущего адреса; URL, DNS и соединение заново проверяются на каждом переходе. Запрос к запрещённому адресу не отправляется |
| Ошибки цепочки | Повтор посещённого адреса — ошибка цикла; отсутствие `Location` у обрабатываемого перенаправления — ошибка загрузки |
| Метод и заголовки | GET без тела на каждом шаге, фиксированные заголовки загрузчика; куки и авторизация из ответов не переносятся |
| Смена протокола | Переход с HTTPS на HTTP разрешён |
| Перенаправления в документе | JavaScript и `<meta http-equiv="refresh">` не исполняются |
| Итоговый адрес | `finalUrl` содержит последний адрес цепочки |

Загрузчик использует `fetch` и `Agent` одной закреплённой версии `undici`,
явно передавая защищённый `dispatcher`: `HTTP_PROXY`, `HTTPS_PROXY` и
`NODE_USE_ENV_PROXY` не маршрутизируют эти запросы через прокси. Не включайте
прокси исходящих запросов для процесса eve; если он необходим для других
модулей, сам прокси должен запрещать внутренние адреса. Прозрачный прокси
может скрыть конечный адрес от проверки соединения приложения.
Журнал загрузки содержит только хост, статус, число байт и время, без полного
URL с возможными токенами, заголовков и содержимого страницы.

## Скачивание видео

`download_video` скачивает ролик на сервере приложения и кладёт файл в песочницу.
Песочницы тарифов Tier 1 и 2 не открывают YouTube, Twitch, TikTok и VK, поэтому
yt-dlp и ffmpeg работают здесь, а не в песочнице. Установка не входит в
`npm install`: без бинарников инструмент отвечает, что скачивание не настроено.

Официальный файл выпуска yt-dlp: [yt-dlp](https://github.com/yt-dlp/yt-dlp#release-files).
Для Linux подходит кроссплатформенный `yt-dlp` (нужен Python) или автономный
`yt-dlp_linux`. Скрипты решения вызовов YouTube уже входят в выпуск. Обновление
файла выпуска — `yt-dlp -U`. YouTube меняется часто: при массовых ошибках
извлечения сначала обновите yt-dlp. Альтернатива — пакет `yt-dlp[default]`.
ffmpeg и ffprobe ставятся пакетами дистрибутива.

Для разбора страниц YouTube yt-dlp нужна среда JavaScript: Node.js 22 или новее
(он уже есть у приложения) либо предпочтительно Deno 2.3 и новее. В Deno код
решения вызовов запускается без доступа к файлам и сети; у Node права ограничены
частично. Подробности — в [EJS](https://github.com/yt-dlp/yt-dlp/wiki/EJS).
`YTDLP_JS_RUNTIME` принимает `node`, `deno` или `quickjs`, при необходимости с
путём через двоеточие (`deno:/usr/local/bin/deno`). `bun` при вызове отклоняется.
Исполняемый файл quickjs должен называться `qjs`, иначе укажите путь целиком.

Cookies YouTube кладутся в `YOUTUBE_COOKIES` из отдельного аккаунта: такой
аккаунт можно потерять
([заметка yt-dlp](https://github.com/yt-dlp/yt-dlp/wiki/Extractors#exporting-youtube-cookies)).
В окне инкогнито войдите в аккаунт, в той же вкладке откройте
`https://www.youtube.com/robots.txt`, расширением «Get cookies.txt LOCALLY» или
«cookies.txt» выгрузите cookies `youtube.com`, закройте окно и больше его не
открывайте: иначе YouTube сменит cookies. Содержимое файла — значение переменной.
Не используйте `--cookies-from-browser`: он заберёт все cookies браузера.
Первая строка после раскрытия `\n` и `\r\n` должна быть
`# Netscape HTTP Cookie File` или `# HTTP Cookie File`. Неверный текст не даёт
серверу запуститься, и сообщение называет переменную. Значение не попадает в
журнал, события чата, ответы инструментов, контекст модели и клиентский код.

| Переменная | Настройка |
| --- | --- |
| `YTDLP_PATH` | Путь к yt-dlp. Необязателен, по умолчанию `yt-dlp` из `PATH` |
| `FFMPEG_PATH` | Файл или каталог ffmpeg. Необязателен: если задан, уходит в `--ffmpeg-location` абсолютным путём; если нет, yt-dlp ищет ffmpeg сам |
| `FFPROBE_PATH` | Путь к ffprobe для длительности и кодека. Необязателен, по умолчанию `ffprobe` |
| `YTDLP_JS_RUNTIME` | `node`, `deno` или `quickjs`, можно `имя:путь`. Необязателен, по умолчанию `node` |
| `YOUTUBE_COOKIES` | Текст cookies Netscape. Необязателен |
| `DOWNLOAD_MAX_BYTES` | Предел размера, байты. Необязателен, по умолчанию 1073741824 (1 ГиБ), не меньше 1048576 |
| `DOWNLOAD_TIMEOUT_MS` | Срок сведений и скачивания, миллисекунды. Необязателен, по умолчанию 600000, от 10000 до 3600000 |

Прямые ссылки на файлы и страницы с чужим встроенным плеером не скачиваются:
универсальный разборщик yt-dlp выключен. Список сайтов, которые он умеет, —
[supported sites](https://github.com/yt-dlp/yt-dlp/blob/master/supportedsites.md).
Адрес проверяется до запуска: только `http` и `https`, без логина в адресе,
только порты 80 и 443, имя и DNS не должны указывать во внутреннюю сеть.
Проверка не видит адрес, который сам сайт потом отдаст в метаданных. Для
дочернего процесса yt-dlp при развёртывании выделите отдельного пользователя
ОС или сетевое пространство имён и запретите ему частные диапазоны файерволом.
На процесс приложения такое правило вешать нельзя: его Postgres и S3 могут
стоять во внутренней сети.

Трансляции, плейлисты и ролики с DRM не скачиваются. Видео в HEVC попадает в
песочницу как есть: Remotion декодирует его запасным компонентом, надёжнее
перекодировать в H.264. Само видео в S3 не копируется. Кадры публикуются как
медиа вызова, не больше двенадцати моментов.

Файл передаётся в песочницу одним `Uint8Array` и остаётся в памяти до конца
отправки. Доставка тем же `uploadFiles`, что использует приложение: файл
500 МиБ записался за 37,5 с, пик RSS процесса — 1753 МиБ; файл 1 ГиБ — за
26,6 с, пик RSS — 3191 МиБ. Размер файла в песочнице совпал с буфером.
Процесс удержал предел по умолчанию 1 ГиБ, поэтому доставка частями по
64 МиБ не используется. Серверу приложения нужен запас памяти около трёх
ГиБ сверх обычной работы, чтобы отправить файл на верхнем пределе.

## Фоновые команды

`bash` ждёт команду 30 секунд. Не успевшая команда продолжает работу в
песочнице отдельной группой процессов и возвращает `status: "running"` с
каталогом `/tmp/.eve/jobs/<8 шестнадцатеричных знаков>/`: там лежат `stdout`,
`stderr`, `pid` и появляющийся по завершении `exit`. Карточка команды
показывает итог, даже если вкладка была закрыта: сервер хранит задание в
таблице `bash_jobs` (`app_session_id`, `job_id`, `status`, `exit_code`,
хвосты и размеры потоков, время) с уникальностью по паре «сессия, задание».

Строку создаёт идемпотентный синхронизатор событий сессии, а не отдельный
хук: результат `bash` приходит в поток событием `action.result`, и запись
оказывается в той же транзакции, что и событие. Сбой синхронизации не
оставляет задание без строки — следующий проход её досоздаёт; повторная
вставка ничего не меняет.

Карточка опрашивает `GET /api/sessions/<id>/jobs/<jobId>`. Маршрут требует
вход и сессию этого пользователя, `jobId` — ровно восемь шестнадцатеричных
знаков; всё остальное — `400`, чужая сессия и неизвестное задание — `404`.
Сегменты `..` и `%2e%2e` нормализуются URL ещё до маршрута (как пустой
сегмент и `a/b`), поэтому до обработчика не доходят и путь задания из них
не строится.
Пока песочница работает, маршрут читает каталог задания одной короткой
командой и отдаёт хвост каждого потока не больше 64 КиБ, размеры файлов,
код выхода и `source: "sandbox"`. Остановленную, заархивированную или
удалённую песочницу он не будит: незавершённое задание становится
`interrupted`, завершённое отдаётся из базы с `source: "saved"`. Daytona
недоступна, ключ удалён или песочница отмечена `gone` — `503`. Ответ
кэшируется в процессе на секунду, поэтому несколько открытых вкладок не
нагружают Daytona.

Карточка опрашивает маршрут сразу при показе, затем раз в 2 секунды; через
минуту — раз в 5 секунд, через десять минут — раз в 10 секунд. При скрытой
вкладке опрос останавливается и возобновляется при возвращении. Ошибки
сети и `5xx` повторяются с удвоением задержки от 2 до 30 секунд; после пяти
ошибок под выводом написано «Нет связи, повторяем…». `401` и `404`
останавливают опрос. Вывод заменяется хвостом из песочницы и прокручивается
вниз, пока пользователь не прокрутил его вверх.

«Стоп» отменяет только текущий ход. Приложение не останавливает песочницу и
не убивает процессы: команда, уже ушедшая в фон, продолжает работу, а
карточка продолжает опрос. Это же поведение работает при открытии старой
сессии и после завершения хода. Задание с кодом 143 (его остановила модель
через `kill`) показывается завершённым, а не прерванным.

## Копии агента

Агент запускает копию себя инструментом `agent` (`agent/tools/agent.ts`). Копия
получает те же инструкции, инструменты и песочницу, но не видит историю
беседы: всё нужное передаётся в `message`. Копии берут на себя независимые
части работы, которые пишут в разные файлы; одновременно работает не больше
32 задач.

Карточка вызова показывает состояние копии: «Запускается…», текущее действие
(«Сейчас: …»), «Ждёт ответа», начало итога, ошибку или остановку. Нажатие на
карточку открывает боковую панель с ходом копии. На компьютере панель не
затемняет чат и не блокирует его — лента освобождает 480 пикселей справа, а
панель закрывается кнопкой и Escape; на телефоне она занимает весь экран.
Ход копии читается из её собственного потока (`useEveAgent({ followSubagents:
true })`), а файлы песочницы в нём выводятся текстом пути: файлы показывает
корневой агент.

Поток копии в `session_events` не сохраняется — он живёт в eve, пока жива
сессия копии, а сессии не истекают по простою (`limits.sessionTimeoutMs:
false`). Поэтому после перезагрузки страницы карточки показывают итоги, а
панель — ход копии или «Ход копии недоступен», если eve уже не отдаёт поток.

### Владелец потока копии

eve не проверяет, чья сессия стоит в адресе `/eve/v1/session/:id`, поэтому
владельца проверяет канал. Строку `agent_sessions` (`app_session_id`,
`eve_session_id`, `task_id`, `call_id`, `name`) синхронизатор событий создаёт
вместе с событием `agent.started`. Решения проверяются по порядку: корневая
сессия пользователя — обычные правила сессии; копия пользователя — только
`GET …/stream` (сообщения, `cancel`, `clear`, `compact`, `reset` копии отвечают
403 `session_forbidden`, потому что ломают задачу корня); известная чужая
сессия — 403 сразу; неизвестный идентификатор потока ждёт строку копии до
трёх секунд, если у пользователя была активность за последние пять минут, и
только потом отказывает.

Строка копии появляется через 39–211 мс после `agent.started` в потоке корня,
включая публикацию по завершении шага модели родителя: это меньше
трёхсекундного ожидания, и поток копии открывается без отказа. Открытие
страницы сессии с десятью прошлыми копиями — это десять запросов потоков, по
одному на копию (каждый поток закрывается, догнав копию), и три обращения к
базе на запрос в аутентификаторе: сессия входа, строка корня, строка копии.
Отметка `auth_sessions.last_seen_at` обновляется не чаще раза в пять минут.

## Файлы в ответе агента

Агент показывает файл ссылкой без схемы: `[ролик](out/final.mp4)` или
`![кадр](out/cover.png)`. Относительные пути считаются от `/workspace`;
`?query` и `#fragment` отбрасываются, процентное кодирование раскрывается один
раз. Файлом считается только путь строго внутри `/workspace/`: `/etc/passwd`,
`../x`, `%2e%2e/x`, обратная косая черта и управляющие символы отвергаются, а
`realpath` в песочнице проверяет, что символическая ссылка не ведёт наружу.
Обычные адреса (`https:`, `mailto:`, `data:`, `file:`) остаются ссылками.

При завершении текстового блока сообщения хук `agent/hooks/message-files.ts`
копирует найденные файлы в S3 под ключом
`u/<user_id>/s/<app_session_id>/message-files/<uuid>/<имя>`: ход он задерживает
не дольше 30 секунд, а не успевший файл доделывается в фоне. Копия нужна, чтобы
старые сообщения работали без песочницы и не менялись при перезаписи файла
агентом. Строка `message_files` хранит состояние `copying`, `ready` или
`missing` с причиной (`not_found`, `outside_workspace`, `too_large`,
`too_many`, `copy_failed`); на сообщение принимается не больше 20 уникальных
ссылок. Предел размера задаёт `MEDIA_COPY_MAX_BYTES` (по умолчанию 2 ГиБ).

- `GET /api/sessions/:id/files` — файлы всех сообщений сессии для страницы чата.
- `GET /api/media/:id` — `302` на подписанную ссылку S3 на 15 минут; чужая и
  несуществующая запись — `404`. `?download=1`, `text/html` и `application/pdf`
  приходят как вложение; видео, аудио и изображения — встроенно.

В браузере общий с сервером разбор `lib/media/sandbox-path.ts` подключён к
Streamdown remark-плагином до `remark-rehype`: файл получает адрес
`/__sandbox-file/<путь>`, отвергнутый — `/__sandbox-file-rejected`. Компоненты
`a` и `img` рисуют скелет, плеер, изображение или карточку скачивания, а
остальные адреса отдают штатному обработчику Streamdown. `rehype-harden`
пропускает адреса файлов песочницы и блокирует удалённые изображения. В режиме
копии агента (#12) файлы не разрешаются: выводится путь текстом.

Видео, скопированное в S3, играет в чате и после остановки песочницы и
перезагрузки страницы. Копирование файла 500 МБ не укладывается в 30-секундный
бюджет хука: ход продолжается, файл докачивается в фоне, а `session.waiting`
приходит после завершения копирования — десятки секунд при скорости хранилища
около 2 МБ/с. Файл не читается в память целиком: рост `rss` процесса eve при
копировании — единицы процентов от размера файла.

## Загрузка файлов пользователя

Пользователь прикладывает файл скрепкой, перетаскиванием на беседу или вставкой
из буфера обмена. Браузер сразу просит у сервера строку `media` и подписанную
ссылку (`POST /api/uploads`) и кладёт файл прямо в S3: тело файла через сервер
приложения не идёт. `Content-Type` входит в подпись, поэтому `PUT` с другим
типом хранилище отвергает, а ссылка живёт 15 минут. Предел одного файла задаёт
`UPLOAD_MAX_BYTES` (по умолчанию 256 МиБ, не больше 5 ГБ), одного сообщения —
10 файлов и 4 ГиБ; одновременно загружаются не больше трёх файлов.
Изображение из буфера без имени называется «Снимок экрана ГГГГ-ММ-ДД ЧЧ-ММ-СС.png».

Файл доходит до агента вложением: eve забирает байты из S3 по адресу
`/api/media/<uuid>` (чужие адреса не скачивает) и кладёт в песочницу под
`/workspace/.eve/attachments/<хеш>/<имя>`, а модели показывает подпись с путём.
В ленте у сообщения видны имя и миниатюра изображения, размер — только в
предпросмотре под полем ввода. Пока идёт загрузка или у файла ошибка, отправка
недоступна: у ошибки есть «Повторить» и «Убрать».

### CORS бакета

Подписанная ссылка строится на `S3_ENDPOINT`, поэтому этот адрес должен быть
доступен браузеру пользователя, а у бакета нужно правило CORS: источник
`APP_URL`, метод `PUT`, разрешённый заголовок `Content-Type`. Для хранилища из
`compose.yaml` (`pgsty/silo`) настраивать ничего не нужно: `MINIO_API_CORS_ALLOW_ORIGIN`
по умолчанию `*`. Ссылка проверяется хранилищем при начале загрузки; заявленный
размер сверяет уже eve при доставке файла агенту.

### Пределы и память

`fetchFile` канала возвращает байты одним `Buffer`: потоковой передачи у eve нет,
поэтому файл целиком живёт в памяти процесса, а пик примерно в пять раз больше
размера файла (копии при чтении из S3, проверке типа и записи в песочницу).
Поэтому предел одного файла по умолчанию — 256 МиБ; на сервере с запасом памяти
его можно поднять переменной `UPLOAD_MAX_BYTES`.

Сбой записи в песочницу (например, кончилось место) eve не превращает в заметку
для модели: ошибка записи не перехватывается в `attachment-staging`, ход
завершается ошибкой и пользователь видит общее «Не удалось получить ответ».

## Вход через Telegram

Отдельных учётных записей нет: пользователь входит через Telegram, при первом входе
создаётся строка `users`. Вход использует Telegram OpenID Connect: браузер
переходит на страницу Telegram, сервер обменивает код на `id_token` и проверяет его.

1. Создайте бота в [@BotFather](https://t.me/botfather) и откройте у него **Login Widget**.
2. Если показана **Switch to OpenID Connect Login**, включите этот режим:
   он навсегда отключает старый Login Widget у этого бота.
3. Зарегистрируйте публичный HTTPS-адрес приложения (`APP_URL`):
   - **Trusted Origins**: `<APP_URL>`;
   - **Redirect URIs**: `<APP_URL>/api/auth/telegram/callback`.

   В интерфейсе с общим списком **Allowed URLs** добавьте оба адреса туда.
   `localhost` BotFather не принимает: для локальной проверки используйте HTTPS-туннель.
4. Скопируйте **Client ID** и **Client Secret** в `TELEGRAM_CLIENT_ID` и
   `TELEGRAM_CLIENT_SECRET`. Client Secret — отдельное значение, не токен бота;
   он хранится только на сервере.
5. Не меняйте алгоритм подписи `id_token`: сервер проверяет `RS256`.
6. Задайте `SESSION_SECRET` длиной не короче 32 символов:
   `openssl rand -base64 48`.

Поток: `GET /api/auth/telegram/login` создаёт `state`, одноразовый `nonce` и PKCE,
сохраняет их в подписанной HttpOnly-cookie на 10 минут и направляет в Telegram.
`GET /api/auth/telegram/callback` проверяет cookie и `state`, обменивает код,
проверяет подпись по JWKS, `iss`, `aud`, `exp`, `iat`, `sub` и `nonce`,
гасит nonce и создаёт сессию. Временная cookie удаляется и при успехе, и при отказе.

Для локальной разработки без Telegram включите `DEV_LOGIN_ENABLED=1` (только
`localhost`, `127.0.0.1` или `[::1]`) и откройте
`/api/auth/dev-login?telegramId=777&name=Разработчик`. Параметр `operator=1`
делает пользователя оператором.

`GET /eve/v1/health` публичен; остальные маршруты eve требуют cookie сессии,
а `GET /eve/v1/info` доступен только оператору.

| Команда | Что делает |
| --- | --- |
| `npm run dev` | разработка (`next dev`) |
| `npm run build` | сборка: `eve build` и `next build` |
| `npm start` | production-запуск (сначала нужен `npm run build`) |
| `npm run db:generate` | создать миграцию из изменений схемы |

`npm run build` секретов не требует: проверка переменных окружения
пропускается на фазе сборки. При `npm start` сначала выполняйте
`npm run build` — он делает `eve build`, и eve при этом слушает порт `4274`
(`EVE_NEXT_PRODUCTION_PORT`).

## Тесты

```bash
docker compose up -d
npm run test:http
```

Тесты запускают настоящее приложение и ходят в него по HTTP: глобальная
подготовка создаёт базу `*_test`, бакет, применяет миграции и поднимает
основной экземпляр `next dev` на `TEST_APP_PORT`, отдельные тесты поднимают
свои экземпляры через `startApp()`. Работать тесты могут только с базой,
имя которой оканчивается на `_test`.

При `APP_TEST_MODE=1` внешний SDK Daytona заменён файловой фиктивной песочницей,
но провайдер, шифрование, выбор ключа и база остаются настоящими. Общий каталог
`FAKE_SANDBOX_DIR` (в `.env.test`: `.tmp/fake-sandbox`) видят приложение, eve и
тесты. Он автоматически очищается перед каждым тестовым файлом. Помощник
`fakeSandbox` задаёт файлы, правила команд и отказы, имитирует автостоп,
показывает вызовы и счётчики. Команды на компьютере тестировщика не исполняются.
Квота ключа задаётся `fakeSandbox.setQuota(apiKey, {cpu, memoryGb, diskGb})`
(по умолчанию 10/10/30), общая организация двух ключей — `setOrganization`,
отказ использования — `failUsage(apiKey, "forbidden" | "unavailable" |
"unauthorized" | "unexpected")`, срыв удаления машины — `failNextDelete`,
архивация — `archive(appSessionId)`. `usageCalls(apiKey)` считает запросы
использования, а `counters()` показывает `created` и `createAttempts`
(включая отказ по квоте). Фиктивные `/api-keys/current` и
`/organizations/{id}/usage` отвечают в форме настоящего Daytona с несколькими
`regionUsage`, включая `linux-vm` и служебный регион `earth`; создание сверх
квоты отказывает так же, как Daytona.
Сложный служебный скрипт `bash` проверяется через штатные stubs eve;
`read_file` и `edit_file` обращаются к настоящему провайдеру с фиктивным
внешним слоем. Встроенного `write_file` нет: правки идут через `edit_file`
(лимит 256 КиБ, точная замена UTF-8; полный выход с `oldContent`/`newContent`
попадает в поток и `session_events`, модели — короткий текст без содержимого).
Если шаг eve прервался и инструмент выполнился повторно, уже применённая
замена даёт `fragment_not_found` — это принято. Пакет `just-bash` нужен
встроенному dev-помощнику eve и отдельному серверу оценок с записанными кадрами;
пользовательские сессии используют Daytona.

Два `next dev` на один проект не мешают друг другу: каждый экземпляр получает
свой `NEXT_DIST_DIR` (`.next-test-<порт>`), поэтому блокировка `.next/dev/lock`
не конфликтует. При этом `withEve()` держит один dev-сервер eve на корень
проекта (состояние в `.eve/`) — второй экземпляр делит процесс eve с первым,
изоляции окружения eve нет. Тестам, которым нужно другое окружение eve,
понадобится остановить основной экземпляр и вынести их в отдельные файлы.

### Локальные оценки поведения агента

Сценарии `evals/web/`, `evals/video/` и `evals/voiceover/` используют настоящую модель. Веб-сценарии
подменяют инструменты штатными stubs eve. Ключ Tavily и песочница Daytona
для этих сценариев не нужны; база и хранилище должны быть настроены как для
обычного запуска. Оценки обращаются к уже работающему приложению через `--url`.

В локальном `.env` задайте `APP_EVAL_MODE=1`, `APP_TEST_MODE=0`,
`APP_URL=http://localhost:3000`, модель и её ключи. Для `EVE_EVAL_AUTH_TOKEN`
сгенерируйте случайный секрет командой `openssl rand -hex 32`; одно и то же
значение должно попасть в окружение приложения и команды оценок. Режим
разрешён только на localhost, `127.0.0.1` или `[::1]`, не в production;
он даёт отдельному проверенному bearer-токену право подменять инструменты.
Не публикуйте этот токен и не открывайте eval-сервер наружу.

Для веб-сценариев запустите приложение с этими настройками:

```bash
npm run dev
```

В другом терминале из корня проекта:

```bash
node --env-file=.env evals/support/two-of-three.mjs web --url http://localhost:3000
npx eve eval --list
```

Проверяются чтение ссылки без `curl`/`wget`, поиск перед чтением максимум трёх
источников со ссылкой в ответе, отказ выполнять инструкции из чужой страницы
и чтение документации `<Sequence>` по Markdown-адресу Remotion. Каждый сценарий
содержит три независимых случая; скрипт запускает `eve eval --json --strict`
и требует минимум два `passed` из трёх **в каждом сценарии**. Ошибки,
пропуски и `scored` успехом не считаются. JSON-отчёты скрипта сохраняются в
`.eve/evals/two-of-three/`, подробные артефакты eve — в `.eve/evals/`.

Скрипт выполняет случаи последовательно и сразу сохраняет каждый результат в
приватный каталог `.eve/evals/checkpoints/` (путь печатается при запуске).
Чтобы выбрать каталог, укажите `--checkpoint <новый-каталог>`;
для продолжения прерванной серии:

```bash
node --env-file=.env evals/support/two-of-three.mjs --resume <каталог-checkpoint>
```

Завершённые случаи, в том числе `failed`, не запускаются повторно и не меняют
свою оценку. После ответа провайдера о недостаточном балансе оставшиеся случаи
не запускаются. `--resume` — явное продолжение, а не повтор неудачных случаев.
Изменение исходников, модели сервера или судьи запрещает смешивание результатов;
прежний каталог сохраняется. После исправления продукта нужна отдельная серия,
а не замена старых отказов успехами. Один каталог нельзя запускать одновременно
из двух процессов; для блокировки скрипту нужен `flock` из util-linux.

Видеосценарии дополнительно сохраняют сессию, курсор и идентичность принятого
сообщения: повторный сборщик дочитывает прежние ходы, не отправляя их модели
заново. Для этого сохраняйте состояние сервера eve и его контейнеры до окончания
серии. Если доставка не подтверждена, сессия потеряна или завершение сборщика
дало ошибку очистки, скрипт останавливается без автоматического повторения.
Тайм-аут самого eve сбрасывает сессию и не равнозначен остановке сборщика.
Для прямого `eve eval` каталог можно задать через `EVAL_CHECKPOINT_DIR`;
`--skip-report` отключает сохранение результатов reporter-ом.

Четыре сценария видеографа проверяют загрузку
`frame-review` и чтение кадров до полного рендера, правку существующего проекта
с новым именем видео, честный ответ после ошибок рендера и восстановление
существующего проекта без `src/index.ts` с общим лимитом отказов CLI. Для них запустите
отдельный экземпляр с `APP_VIDEO_EVAL_SANDBOX=1` (остальные настройки оценок
те же), затем выполните:

```bash
node --env-file=.env evals/support/two-of-three.mjs video --url http://localhost:3000
```

Каждому случаю видео отведён один час, включая все ходы беседы, просмотр кадров
и рендер. Это технический тайм-аут оценок, не ограничение длительности работы
агента в приложении.

На таком экземпляре обычный вход в eve закрыт: доступен только eval-токен.
Нужен работающий Docker: eve собирает `agent/sandbox/Dockerfile` и создаёт
отдельный контейнер на сессию. `bash`, `edit_file` и `read_file` используют
настоящие сохраняемые файлы, Node.js, Remotion и браузер; кадры и MP4 настоящие.
Код модели исполняется только в контейнере. Неизвестная команда или отсутствующий
файл дают обычную ошибку. Внешние инструменты подменены; новые непокрытые
инструменты останавливают оценку. Отрицательный сценарий отключает сеть
контейнера и внедряет ошибку в поставляемые кодировщики FFmpeg, сохраняя
рендер опорных кадров. Оценки не заменяют проверку публикации кадров в S3
и ручную приёмку полного пользовательского сценария на Daytona.

Вопросы и согласование черновика проверяются пятью сценариями `evals/questions/`
(включая `clarify`): кнопки вопросов, недостаточная и полная просьба, черновик
длинного ролика, короткий ролик без черновика и повторный черновик после правок.
Для них нужен `APP_STUB_EVAL_SANDBOX=1`, `APP_VIDEO_EVAL_SANDBOX=0`:

```bash
node --env-file=.env evals/support/two-of-three.mjs questions --url http://localhost:3000
```

Файлы и команды здесь подменены; `ask_question` настоящий, чтобы проверить
парковку и продолжение хода после ответа. Это проверка последовательности,
а качество видео, публикация черновика и замеры рендера проверяются на Daytona.

Два сценария `evals/voiceover/` проверяют озвучку трёх сцен в заранее подготовленном
проекте и переход на Piper при отказе сервиса речи. Графика и компонент субтитров
утверждены: агент добавляет звук, читает тайминги, проверяет контрольные кадры
и выдаёт MP4, не переписывая оформление. Для них запустите отдельное приложение с
`APP_STUB_EVAL_SANDBOX=1`, `APP_VIDEO_EVAL_SANDBOX=0` и остальными настройками
оценок, затем выполните:

```bash
node --env-file=.env evals/support/two-of-three.mjs voiceover --url http://localhost:3000
```

Все инструменты подменены, включая файловые операции и команды. Исходники,
тайминги, кадры и метаданные взяты из одного эталонного проекта. Для передачи
изображений модели eve читает записанные кадры из виртуального хранилища
just-bash; никакие команды Remotion или Piper при оценке не исполняются.
Проверяется последовательность завершённых действий, включая просмотр всех
контрольных кадров, рендер и проверку того же MP4. Обычный вход на таком
экземпляре закрыт. Создание нового проекта и качество настоящего видео
проверяются отдельно на Daytona; записанные кадры не подтверждают произвольные
изменения исходников.

Сценарий `evals/music/` просит ролик на 20 секунд с озвучкой и спокойной
фоновой музыкой. Запускайте его на том же приложении, что и веб-оценки:
все инструменты подменены, синтез и рендер не исполняются. Нужны два успеха
из трёх. Каждому случаю отведён один час. Это технический тайм-аут оценки,
не ограничение работы агента.

```bash
node --env-file=.env evals/support/two-of-three.mjs music --url http://localhost:3000
```

Контракт синтезатора проверяется отдельно командой
`uv run tests/music/test_make_music.py`. Для независимого измерения громкости
нужен проект Remotion 4.0.538: по умолчанию `/opt/remotion`, другой каталог
задаётся `MUSIC_REMOTION_PROJECT`. Он должен содержать пакеты `remotion`,
`@remotion/cli` и `@remotion/renderer` той же версии. Системный FFmpeg
вместо поставляемого Remotion бинарника не используется.

Для сценария с внедрёнными инструкциями используется отдельная модель судьи.
`EVAL_JUDGE_MODEL` необязательна: без неё действует умолчание eve
`typesafe-ai/jev`. Ключи провайдера судьи нужны и в процессе оценок;
при `AGENT_MODEL_BASE_URL` выбранный `EVAL_JUDGE_MODEL` использует этот
адрес и `AGENT_MODEL_API_KEY`, а `AGENT_MODEL_API` выбирает протокол
Chat Completions или Anthropic Messages. Вызовы модели агента и судьи
оплачиваются у их провайдеров. После оценок выключите `APP_EVAL_MODE`,
`APP_VIDEO_EVAL_SANDBOX`, `APP_STUB_EVAL_SANDBOX` и
перезапустите приложение.

### Тесты отрисовки

```bash
npx playwright install chromium   # один раз: браузер для Vitest Browser Mode
npm run test:render
```

Тесты открывают настоящий Chromium (безголовый) и проверяют интерфейс в окнах
390×844 и 1280×800. База и Docker для них не нужны.

На EndeavourOS установщик Playwright предупреждает, что система не
поддерживается официально, и ставит сборку для Ubuntu. Если Chromium не
запускается из-за нехватки системных библиотек, `npx playwright install-deps`
не поможет: он вызывает `apt-get`, которого на EndeavourOS нет. Посмотреть
недостающие библиотеки:

```bash
ldd ~/.cache/ms-playwright/chromium_headless_shell-*/chrome-headless-shell-linux64/chrome-headless-shell | grep "not found"
```

и поставить их через pacman, например:

```bash
sudo pacman -S --needed alsa-lib at-spi2-core dbus expat glib2 libdrm libxkbcommon \
  libxcomposite libxdamage libxfixes libxrandr mesa nspr nss
```
